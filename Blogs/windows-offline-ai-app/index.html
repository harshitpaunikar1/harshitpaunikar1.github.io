The real edge is not a specialized hardware rack in a datacenter. It is an underpowered Windows 10 tablet on the passenger seat of an inspection truck -- dual-core CPU, intermittent cellular signal, and a technician who needs to classify a defect right now, not after driving back to the office.

When we loaded the standard PyTorch model on these tablets, it consumed nearly all available RAM, took 4.2 seconds per inference, and drained the battery in three hours. A technician inspecting 40 poles in a day would lose their device before lunch. We needed a fundamentally different approach.

[PANEL_01: HARDWARE LIMITS & QUANTIZATION]

We could not change the physical hardware, so we had to change the model. Standard neural networks use FP32 (32-bit floating point) weights, providing high precision at the cost of large memory allocation and slow matrix multiplication on a CPU.

The core deployment strategy was converting the original model to ONNX (Open Neural Network Exchange) format and applying INT8 Quantization. Quantization aggressively rounds 32-bit floating-point calculations into 8-bit integers. While this risks slight accuracy degradation (typically under 2%), it reduces the model footprint by 75% and massively accelerates CPU execution because integer math is far cheaper than floating-point math.

CPU Execution Target > ORIGINAL: RetinaNet FP32 | 148MB | ~4.2s/frame [REJECTED]
> DEPLOYED: ONNX INT8 | 37MB | ~320ms/frame [ACCEPTED]

By bounding the inference to under 500 milliseconds, the application maintains the illusion of an interactive, real-time tool rather than an unresponsive processing script.

[PANEL_02: PERSISTENCE & DEFERRED SYNC]

An application operating in a concrete basement will experience 100% packet loss. If the inference pipeline attempts an API call to save data, the application hangs.

To survive disconnection, the application treats the cloud as an eventual convenience, not a runtime dependency. ONNX inference deposits results directly into a local SQLite database on the tablet's hard drive. The SQLite file acts as an immutable queue: the user captures an image, the model infers a defect, the local database logs the row, and the UI immediately clears for the next capture.

A background SyncWorker thread runs continuously, pinging for network availability. When the technician drives into a 4G zone, the worker detects connectivity and quietly drains the SQLite logs via bulk REST payloads to the central server. If the connection drops mid-sync, the transaction rolls back locally and retries an hour later.

[PANEL_03: DEPLOYMENT PRAGMATISM]

Shipping updates to tablets on the move demands minimal friction. We avoided convoluted Docker architectures that struggle on obscure Windows builds. The application is packaged as a self-contained binary using standard Windows installers (MSI), carrying the required ONNX runtime DLLs locally. The entire application directory lives outside OS update paths so Microsoft Patch Tuesdays do not silently brick the ML dependencies.

Building for boring hardware enforces discipline. When you cannot rely on a GPU to mask inefficient code, you write efficient code. When you cannot rely on LTE, you build bulletproof local persistence. The resulting application has no architectural vanity: it launches instantly, infers reliably, and never loses the user's data.

[PANEL_04: PROJECT CONTEXT]

The client was a utility company with 60 field technicians inspecting power line equipment across three service regions. Their existing workflow depended on a cloud-based defect detection system that required a strong internet connection. The problem: roughly 40% of inspection sites -- rural areas, underground substations, remote corridor sections -- had no reliable connectivity.

When technicians hit a dead zone, they reverted to manual processes: photograph every defect, drive back to the office, classify everything by hand. This created a backlog that grew weekly and introduced errors from delayed classification -- a cracked insulator photographed in the morning looked different on a screen eight hours later without the physical context.

[PANEL_05: RESULTS & IMPACT]

The deployment covered all 60 tablets across three service regions. The numbers reflected a complete shift from office-based reclassification to on-site real-time detection.

Model size dropped from 148MB (PyTorch FP32) to 37MB after ONNX conversion and INT8 quantization -- a 75% reduction. Inference speed went from 4.2 seconds per frame to 320 milliseconds, 13 times faster. The application ran comfortably on the 2-core tablets with 4GB of RAM and no GPU. Post-quantization accuracy held at 94.1%, compared to the 95.8% FP32 baseline -- a 1.7% trade-off that the client's quality team deemed acceptable for field use.

The offline inspection backlog was completely eliminated. Technicians now classify defects on-site in real time, and data syncs automatically when tablets reconnect. Monthly time savings across the 60-person field team totaled roughly 180 hours -- time previously spent on manual reclassification back at the office.

[PANEL_06: LESSONS LEARNED]

The first attempt was straightforward and wrong. We tried running the full PyTorch model directly on the tablets. It consumed nearly all available RAM, took 4.2 seconds per inference, and drained the battery in about three hours. A technician inspecting 40 poles per day would lose their device before lunch.

ONNX conversion alone improved things significantly, dropping inference to 1.1 seconds. But that was still too slow for the rapid-fire capture workflow technicians needed. INT8 quantization was the final push that brought inference down to 320 milliseconds, making the tool feel instant.

The Real Complexity Was Not The Model > MODEL OPTIMIZATION: Hard, but well-documented path (PyTorch -> ONNX -> INT8)
> SQLITE SYNC QUEUE: Harder than expected - conflict resolution was the real fight
> SCENARIO: Same inspection modified on tablet AND in office while offline
> SOLUTION: Last-write-wins with full audit trail and manual conflict review queue

The biggest surprise was that the SQLite offline queue turned out to be more complex than the model optimization itself. Model conversion followed a well-documented path: export to ONNX, calibrate, quantize. But the sync layer had to handle a tricky real-world scenario: what happens when a technician modifies an inspection record on their tablet while someone at the office also modifies the same record in the central system? We built a last-write-wins strategy with a full audit trail and a manual conflict review queue for disputed records.

If we built this again, we would add a model update distribution system from day one. Currently, retraining the detection model with new defect types requires a manual update across 60 tablets. An automatic push mechanism -- downloading new model versions over WiFi when tablets charge overnight at the depot -- would have saved significant maintenance effort.
