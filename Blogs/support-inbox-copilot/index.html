Automation with Control: The Bound Support Copilot

The central metric of customer support is resolution accuracy, not reply speed. When AI is integrated into an inbox purely to maximize ticket deflection, the result is hallucinated policies, infuriated users, and reputational damage. A sustainable support architecture treats AI not as an autonomous responder but as a rigid drafting layer gated by human oversight.

My Role: I built the ML pipeline -- embedding-based semantic triage, the confidence threshold system, retrieval grounding against Shopify/Zendesk/Stripe, and the draft generation layer. The support ops lead was the other half of the team: they set confidence thresholds based on real historical ticket data. When the first version over-automated (causing an incorrect refund confirmation in week one), their domain knowledge identified exactly where the cutoff needed to drop.
Stack: Vector embeddings LLM Python Zendesk API Shopify API Stripe API Confidence thresholds

Deploying a Large Language Model directly connected to a customer email address is a profound operational error. LLMs are structurally inclined to appease the user -- issuing unauthorized refunds, inventing feature timelines, and apologizing for system mechanics that are functioning exactly as intended.

A Support Copilot should not be defined by its text generation capabilities. Its value is defined by its routing thresholds: knowing precisely when to act, when to prepare a draft for a human, and when to refuse engagement entirely. We achieved this by inserting a deterministic confidence threshold into the semantic triage pipeline.

[BOUNDARY 01] Semantic Triage & Thresholds

Every inbound ticket undergoes semantic classification before a response is even considered. The system generates an embedding of the customer's text and compares it against hundreds of historically resolved tickets stored in a vector database. Crucially, the system calculates a Confidence Score (0.0 to 1.0) representing the semantic proximity of the current ticket to established, resolved templates.

Threshold Engine Constraints

[> 0.92] AUTO_RESOLVE: Standardized, zero-friction requests (e.g., "Where is my tracking link?"). The system fetches the tracking API, generates the reply, and sends it autonomously. Zero human touch required.

Threshold Engine Constraints

[0.65 - 0.91] COPILOT_DRAFT: Mid-variance requests (e.g., "My order is delayed and I want to change the address"). The system gathers order data, drafts the reply using brand voice, and queues it in the agent's staging area. It does not send.

Threshold Engine Constraints

[< 0.64] MANUAL_ESCALATION: High-friction or emotional requests (e.g., "Your update deleted my account data"). The LLM is bypassed entirely. The ticket is immediately routed to a senior tier-two human agent. No draft is attempted to avoid anchoring bias.

[BOUNDARY 02] The Human-in-the-Loop Interface

When a ticket falls into the COPILOT_DRAFT tier, the objective changes. The AI is no longer operating automatically; it is merely preparing an environment for the human support agent. The interface the human interacts with determines the ultimate safety of the response.

We designed the dashboard to prevent "review fatigue." When an agent opens the ticket, the drafted text is displayed alongside explicitly highlighted data variables. If the AI hallucinated an order number, the interface forces the agent to physically click on the data variables to verify their source payload. Human operators are not treated as secondary observers; they hold the override keys.

COPILOT OVERRIDE MODE :: TICKET #45902

[ SYSTEM ] Context loaded. Sentiment: Frustrated. Resolution type: Address modification.
[ DRAFT ] Attached below. Review before execution.

Hi Sarah,

I understand you need to reroute your recent order. I have successfully updated the destination address to [1442 Oak Avenue, Chicago IL] and confirmed the carrier intercept.

Best.

[BOUNDARY 03] Data Grounding over Guesswork

Generative text without grounding is fiction. To ensure copilot drafts are rooted in reality, the retrieval architecture operates in a constrained chain. Before the LLM generates a single token, it executes rigid API calls -- fetching the user's Shopify order history, Zendesk historical interactions, and Stripe invoice states. The prompt is injected with this JSON payload alongside a strict instruction: If the intent requests a refund and the Stripe payload indicates the window has passed, decline the request regardless of sentiment.

By enforcing this workflow, we strip the language model of its most dangerous feature: autonomy. The copilot succeeds precisely because the engineering team builds walls around it -- treating the AI as a fast drafting assistant tethered to the database and gated by the human operator.

[BOUNDARY 04] Project Context

This system was built for an e-commerce company receiving 800+ support tickets per day. Their previous chatbot was an unbounded GPT wrapper connected directly to the customer inbox. It had no retrieval grounding, no confidence thresholds, and no human oversight layer. It simply generated responses based on whatever the customer wrote.

The consequences were predictable. The bot hallucinated order statuses, invented return policies that did not exist, and in one incident promised a customer a full refund on a non-returnable item. That single mistake cost $2,400 and was shared widely on social media. The bot was shut down, and the support team reverted to handling every ticket manually -- creating a 4-hour response queue.

The project team was 1 ML engineer and 1 support operations lead, working over a 10-week build. The support ops lead was essential because they understood the actual ticket patterns, knew which categories were safe to automate, and could validate the confidence thresholds against real historical data.

[BOUNDARY 05] Results & Impact

The bound copilot replaced the old chatbot with dramatically different outcomes. The core improvement was not speed but accuracy.

The false escalation rate (tickets sent to humans that did not actually need human attention) settled at 9%. This was an acceptable trade-off: a 9% over-escalation rate meant the system was cautious, and cautious was exactly the design intent. Monthly cost savings reached $18K in reduced support staffing needs.

[BOUNDARY 06] Lessons Learned

The first version of the threshold system used 0.80 as the auto-resolve cutoff. This seemed reasonable during testing against historical data. In production, it was too aggressive. Three incorrect auto-resolutions occurred in the first week. One of them told a customer their refund had been processed when it had not.

Threshold Adjustment

Raising the auto-resolve threshold from 0.80 to 0.92 reduced the auto-resolution rate from 65% to 52%, but eliminated incorrect auto-resolutions entirely. The 13% of tickets that moved from auto-resolve into the draft-for-review tier still got fast responses, just with a human checking the answer first. The trade-off was clearly worth it.

The biggest surprise was which feature the human agents valued most. It was not the auto-resolution layer (which they never saw). It was the "draft for review" middle tier. Agents said that having a pre-written response to edit was dramatically faster than writing from scratch. Even when they rewrote 80% of the draft, having the order data already pulled and the response structure already laid out saved them several minutes per ticket.

If building this again, the clear improvement would be per-category confidence thresholds. Billing questions carry higher risk and should require a higher confidence score to auto-resolve. Simple FAQ questions (store hours, shipping zones) could safely auto-resolve at a lower threshold. A single global threshold works, but category-specific thresholds would improve both safety and resolution rates.
